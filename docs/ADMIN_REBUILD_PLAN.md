# План полной пересборки административного интерфейса

Статус документа: проектирование. Целевая ветка: `rebuild/admin-workspace-from-zero`. Production: `main`.

## Цель

Заменить устаревшую компоновку административной панели на новый рабочий интерфейс, сохранив действующие бизнес-операции, интеграцию с Supabase, серверные проверки доступа и публичные маршруты. Это не косметический редизайн и не отдельный демонстрационный продукт.

## Принципы, которые нельзя нарушать

1. Не менять схему Supabase и миграции ради интерфейса.
2. Не переносить бизнес-права в frontend и не ослаблять RLS/Edge Functions.
3. Не смешивать независимого Master_pro с корпоративным Master.
4. Не удалять и не переименовывать существующие действия до проверки всех мест использования.
5. Не менять авторизацию, маршрутизацию публичных страниц и механизм GitHub Pages без необходимости.
6. Любые операции изменения данных должны продолжать использовать существующие защищённые RPC, Edge Functions и разрешённые Supabase-запросы.
7. Доступность интерфейса: desktop, tablet и mobile; состояния загрузки, ошибки, пустые списки и подтверждения опасных действий обязательны.

## Новая информационная архитектура Owner

Основной рабочий контур Owner строится вокруг объектов и задач, а не вокруг старых наборов виджетов.

- **Обзор** — сводка по платформе, сигналы внимания и быстрые переходы к проблемным объектам.
- **Учётные записи** — единый реестр с поиском, фильтрами по роли/статусу/компании, выбором записи и контекстной карточкой действий.
- **Компании** — реестр организаций с показателями сотрудников и страниц, статусом, редактированием и безопасным удалением.
- **Master_pro** — отдельный реестр независимых специалистов и их индивидуальных страниц; не объединять с корпоративными сотрудниками.
- **Системные настройки** — только реально существующие настройки интерфейса/платформы. Не показывать фиктивные переключатели.

Навигация постоянная и компактная. На широком экране — боковая панель и рабочая область; на узком — адаптивная навигация и полноширинные панели. Детали выбранного объекта открываются в отдельной панели/диалоге, не превращая страницу в длинную таблицу с набором раскрывающихся блоков.

## Существующие возможности, которые должны остаться

### Owner / платформа
- вход через Supabase Auth, восстановление сессии и корректная обработка отсутствующей сессии;
- обязательная смена временного пароля;
- загрузка профиля, каталогов компаний/страниц и списка аккаунтов;
- создание учётной записи с назначением роли и компании/страницы;
- изменение имени и назначения роли/компании/страницы;
- включение и отключение аккаунта через `owner-set-account-status`;
- сброс доступа через `owner-reset-access`;
- удаление аккаунта через `owner-delete-user`;
- создание, редактирование, включение/отключение и удаление компании;
- создание и управление корпоративными страницами мастеров и индивидуальными страницами;
- проверка уникальности slug и имени индивидуальной страницы;
- управление публикацией индивидуальных страниц на уровне Owner;
- режим предварительного просмотра рабочих пространств по ролям, если он реализован текущим маршрутизатором и авторизацией;
- уведомления об успехе/ошибке и блокировка повторных действий во время запроса.

### Корпоративный Admin / Master
- сохранить текущий рабочий контур StaffWorkspace;
- загрузка мастеров и связанных данных компании;
- услуги: добавление и включение/отключение;
- регулярное расписание и выходные/исключения;
- редактирование корпоративной страницы;
- просмотр записей и отмена записей в пределах полномочий;
- не давать корпоративному Admin/Master доступ к Master_pro.

### Независимый Master_pro
- сохранить MasterProBuilder и его реальные сценарии: обзор, профиль/страница, дизайн, услуги, расписание, записи, настройки;
- сохранение страницы и настроек, публикация/снятие с публикации;
- загрузка фото/обложки в существующее хранилище;
- управление услугами, рабочими часами, исключениями, параметрами записи;
- просмотр, фильтрация, отмена и завершение бронирований;
- не привязывать к компании.

## План реализации

### Этап 1 — инвентаризация и проектирование
- прочитать все используемые административные компоненты, стили, маршруты, типы и backend-вызовы;
- построить карту действий и матрицу ролей;
- зафиксировать новые сценарии и структуру компонентов;
- определить безопасные границы между UI и текущими операциями данных.

### Этап 2 — новый Owner workspace
- создать новую композицию и навигацию с нуля;
- перенести текущие действия через существующие обработчики/сервисы;
- реализовать новые списки, поиск, фильтры, детали объекта, формы и подтверждения;
- обеспечить responsive-состояния.

### Этап 3 — интеграция рабочих пространств
- встроить корпоративный Admin/Master и Master_pro в единый визуальный язык;
- сохранить раздельные маршруты и права;
- проверить все сохранения и операции.

### Этап 4 — проверка
- TypeScript и production build;
- имеющиеся тесты и CI;
- проверки авторизации и смены пароля;
- smoke-тесты ключевых действий по каждой роли;
- проверка отсутствия изменений Supabase schema;
- публикация preview и проверка доступности реальной сборки.

### Этап 5 — внедрение
- открыть PR в `main`;
- проверить diff, CI, deployment и фактическую production-страницу;
- после успешных проверок выполнить merge;
- проверить вход и ключевые маршруты после внедрения;
- сохранить контрольную точку предыдущего состояния.



## Текущее состояние реализации (10 ноября 2026)

Статус: активная разработка, не готово к production-переходу.

Подтверждённо реализовано в ветке `rebuild/admin-workspace-from-zero`:
- новые каталоги Owner для учётных записей и компаний используются как основные разделы;
- карточки деталей учётной записи и компании с контекстными действиями;
- отдельная карточка управления Master_pro с публикацией и архивированием;
- единый слой адаптивного оформления для Owner и рабочих пространств;
- корпоративный Master может редактировать только назначенное ему рабочее пространство; режим просмотра Owner остаётся read-only;
- статусы записей в корпоративном кабинете переведены на понятные подписи, добавлено пустое состояние;
- обзор Master_pro рассчитывает число записей за текущий день с учётом часового пояса специалиста.

Последняя CI-проверка на актуальном HEAD `8d74d74b2375787e14a27123e49411368c520de7` завершилась успешно (workflow run `42803768151`, job `129787938648`): TypeScript/Vite build, dependency audit, запуск локального Supabase, применение всех миграций, migration status, DB functional tests, Edge Functions typecheck и остановка тестового стека.

Оставшиеся обязательные пункты до перехода:
1. Проверка матрицы доступа Owner / Admin / Master / Master_pro, включая read-only preview.
2. Smoke-тест входа, первого входа со сменой пароля, создания/изменения/отключения учётной записи, управления компанией, услугами, расписанием и записями.
3. Публикация реальной preview-сборки и визуальная проверка в браузере на desktop и mobile.
4. Проверка production deployment и только затем внедрение в `main`.

До выполнения этих пунктов PR остаётся черновым, а production `main` не изменяется.

## Критерии готовности

Новая админка не считается готовой только потому, что проект компилируется. Готовность означает: все перечисленные сценарии доступны, серверные ограничения не ослаблены, build и CI успешны, preview опубликован, основные роли и операции проверены, production после merge открывается без регрессий.
