# Workflows — актуальная архитектура

Документ описывает фактическое состояние проекта на ветке `main`, а не первоначальный план разработки.

## 1. Система и окружения

- Frontend: React 19, TypeScript, Vite, React Router.
- Хостинг frontend: GitHub Pages, базовый путь `/workflows/`.
- Backend: Supabase PostgreSQL и Auth.
- Серверная логика: Supabase Edge Functions и PostgreSQL RPC.
- Контроль доступа: RLS, SQL constraints, функции с ограниченным `EXECUTE`.
- CI/CD: GitHub Actions.
- Основная рабочая ветка: `main`; GitHub Pages и backend deployment следуют за `main`.

Supabase:
- Project ref: `cetcxttaqtberrntsntr`.
- API URL: `https://cetcxttaqtberrntsntr.supabase.co`.
- Проект называется `workflows-DB`.

Публичный publishable key может использоваться в frontend. Service-role/secret key хранится только на стороне Supabase и не должен попадать в браузер, GitHub Pages или переменные `VITE_*`.

## 2. Маршруты

| Маршрут | Назначение |
|---|---|
| `/pro/:slug` | Публичная индивидуальная страница Master_pro |
| `/:companySlug` | Публичная страница компании |
| `/:companySlug/:masterSlug` | Публичная страница мастера компании |
| `/admin/*` | Вход и административные/рабочие интерфейсы |
| `/admin/master-pro-builder` | Авторизованный конструктор индивидуальной страницы Master_pro |
| `/demo`, `/demo/**` | Изолированный демонстрационный режим |

Slug компаний уникален глобально. Системные slug `admin`, `demo`, `pro` зарезервированы на уровне frontend, Edge Function и БД.

Slug индивидуальных страниц Master_pro уникален среди индивидуальных страниц. Неархивированные индивидуальные страницы также не могут иметь одинаковое имя после trim, схлопывания пробелов и приведения к нижнему регистру. Архивные страницы не блокируют повторное использование имени.

## 3. Роли и модель доступа

### Owner
Владелец платформы. Может:
- создавать и удалять учётные записи сотрудников;
- назначать и менять роли;
- создавать, редактировать, включать, отключать и удалять компании;
- управлять страницами мастеров;
- включать и отключать индивидуальные страницы Master_pro;
- управлять услугами, расписанием и бронированиями;
- просматривать данные всех компаний и мастеров;
- сбрасывать временные пароли.

### Admin
Администратор конкретной компании. Может:
- редактировать описание и оформление своей компании;
- создавать, отключать и архивировать только страницы мастеров своей компании;
- не видеть индивидуальные страницы Master_pro и не управлять их публикацией;
- редактировать имена, описания и фотографии мастеров;
- управлять услугами и расписанием мастеров своей компании;
- просматривать записи и клиентскую историю в своей компании.

Admin не создаёт учётные записи и не назначает роли.

### Master_pro
Самостоятельный мастер вне компании. Может:
- редактировать собственную индивидуальную страницу;
- самостоятельно включать и отключать публикацию только собственной страницы;
- управлять собственными услугами;
- управлять собственным расписанием;
- просматривать собственные записи и клиентскую историю;
- отменять собственные записи в рамках серверных правил.

### Master
Сотрудник компании, связанный с одной корпоративной страницей мастера. Может просматривать собственные записи и клиентскую историю. Не редактирует страницу, услуги или расписание и не отменяет записи.

Роль Admin/Master в компании хранится в `company_members`. У профиля при таком назначении `platform_role` остаётся `pending`; роль определяется членством в компании. Для Owner и Master_pro используется `profiles.platform_role`.

## 4. Авторизация и учётные записи

- Вход выполняется по email и паролю через Supabase Auth.
- Email — идентификатор входа и уникальное поле профиля.
- Телефон `+7XXXXXXXXXX` хранится как контактный номер, а не как логин.
- Публичная самостоятельная регистрация сотрудников не предусмотрена.
- Учётные записи создаёт Owner через Edge Function `create-user`.
- Временный пароль должен быть заменён при первом входе.
- Owner может сбросить доступ; после сброса пользователь обязан сменить временный пароль.
- Отключённые профили и профили с обязательной сменой пароля не получают рабочие права.
- Первый Owner создаётся контролируемым bootstrap-процессом через доверенную административную сессию Supabase.

Edge Functions проверяют JWT и повторно проверяют роль/статус вызывающего пользователя на сервере. Данные роли из frontend не считаются доверенными.

## 5. Структура базы данных

В схеме `public` используются 11 основных таблиц:

| Таблица | Назначение |
|---|---|
| `profiles` | Профили сотрудников, email, контактный телефон, platform_role, статус и принудительная смена пароля |
| `companies` | Компании, slug, описание, обложка, тема, часовой пояс и активность |
| `company_members` | Привязка профиля к компании и роль Admin/Master |
| `masters` | Индивидуальные и корпоративные публичные страницы мастеров |
| `services` | Услуги, длительность, стоимость и порядок |
| `working_hours` | Регулярное недельное расписание |
| `schedule_exceptions` | Выходные и исключения на конкретные даты |
| `booking_settings` | Горизонт записи, минимальное время до записи, шаг и текст правил |
| `clients` | Единая клиентская база по нормализованному телефону |
| `bookings` | Бронирования и snapshot-данные услуги/клиента |
| `booking_status_history` | История изменения статусов бронирования |

Связи:
- `profiles.id → auth.users.id`.
- `company_members.profile_id → profiles.id`.
- `company_members.company_id → companies.id`.
- `company_members.(master_id, company_id) → masters.(id, company_id)` (составной FK гарантирует, что страница принадлежит той же компании; при удалении страницы удаляется и членство Master).
- `masters.company_id → companies.id` для корпоративных страниц.
- `masters.profile_id → profiles.id` для индивидуального Master_pro или связанного сотрудника.
- `services.master_id`, `working_hours.master_id`, `schedule_exceptions.master_id`, `booking_settings.master_id` → `masters.id`.
- `bookings.master_id → masters.id`, `bookings.(service_id, master_id) → services.(id, master_id)`, `bookings.client_id → clients.id`.
- `booking_status_history.booking_id → bookings.id`.

Схема использует внешние ключи, составные внешние ключи, уникальные ограничения, CHECK constraints и индексы. БД не позволит привязать сотрудника к странице другой компании или создать бронирование с услугой другого мастера. Эти правила дополнительно проверяются RPC/Edge Functions.

### Удаление и архивирование

- Страницы с услугами или историей бронирований архивируются.
- Страницы без услуг и истории могут удаляться.
- Удаление компании не удаляет учётные записи сотрудников: членства удаляются, профили переводятся в `pending`.
- История бронирований сохраняется через snapshot-поля; ссылка на удалённую услугу может обнуляться, а мастер с историей не удаляется.
- Удаление профиля проходит через Owner Edge Function и серверную очистку/архивирование связанных страниц.

### Целостность бронирования

- `bookings_no_overlap` — exclusion constraint GiST запрещает пересечение подтверждённых бронирований одного мастера.
- `ends_at > starts_at`.
- Цена и длительность snapshot проверяются CHECK constraints.
- `create_booking` повторно проверяет активность мастера/компании/услуги, принадлежность услуги мастеру, расписание, исключения, горизонт, минимальный lead time, телефон и согласие с правилами.
- `get_available_slots` возвращает доступные интервалы.
- Защита от двойного бронирования находится в БД и не зависит от frontend.

## 6. RLS и серверные функции

RLS включён на всех основных таблицах `public`.

Публичный доступ ограничен чтением активных публичных страниц, услуг, расписания и вызовом RPC для проверки слотов/создания бронирования. Доступ сотрудников определяется Owner/Admin/Master_pro/Master и принадлежностью к конкретному мастеру/компании.

Вспомогательные SECURITY DEFINER-функции `is_owner`, `is_company_admin`, `can_manage_master`, `can_view_master` размещены в непубличной схеме `private`; доступ к ней предоставлен authenticated, но схема не выставлена через Data API. В `public` оставлены SECURITY INVOKER-обёртки для RLS и совместимости. Публичные `create_booking` и `get_available_slots` — намеренно доступные RPC для гостевого сценария бронирования; обе функции выполняют серверную валидацию. `cancel_booking` доступна authenticated и проверяет права внутри функции. Для новых функций в `public` права `EXECUTE` больше не выдаются anon/authenticated автоматически: миграция должна явно выдать только необходимые разрешения.

### Edge Functions

| Функция | Назначение |
|---|---|
| `create-user` | Создание сотрудника и первичного назначения |
| `assign-user-role` | Переназначение роли существующей учётной записи |
| `change-password` | Обязательная смена временного пароля |
| `owner-reset-access` | Сброс доступа Owner |
| `owner-set-account-status` | Включение/отключение учётной записи |
| `owner-delete-user` | Удаление учётной записи с очисткой/архивированием |
| `owner-update-account-name` | Изменение имени учётной записи |
| `owner-delete-company` | Удаление/архивирование компании |

Для всех deployed functions включена проверка JWT. Функции, требующие Owner, дополнительно проверяют активную Owner-сессию внутри обработчика.

## 7. Публичная запись

- Одна запись относится к одному мастеру и одной услуге.
- Значения услуги и клиента копируются в snapshot-поля бронирования.
- Клиент не создаёт аккаунт.
- Телефон клиента уникален в `clients`.
- Запись подтверждается автоматически после успешной серверной проверки.
- Клиент не может самостоятельно отменить/перенести запись.
- Настройки по умолчанию: горизонт 30 дней, минимальный lead time 10 минут, шаг 15 минут.
- `booking_settings.rules_text` хранится в БД, но публичный текст правил пока не связан с этим полем: интерфейс показывает фиксированный текст, а RPC проверяет только факт передачи согласия. Полноценный интерфейс редактирования правил ещё не реализован.

## 8. Интерфейс и незавершённые части

- Основная административная панель использует актуальные компоненты управления учётными записями, компаниями, страницами и рабочими пространствами.
- Компоненты с историческим именем `Prototype` могут быть действующими частями текущего интерфейса; само имя не означает, что их можно удалять.
- `MasterProBuilder` загружает индивидуальную страницу текущего аутентифицированного Master_pro и сохраняет профиль, тему/метаданные (`specialty`, `cover_title`, `tags`), услуги, регулярное расписание и горизонт записи через транзакционную RPC `public.save_master_pro_builder` (SECURITY INVOKER, с проверкой `private.can_manage_master`).
- Фотографии профиля и обложки загружаются в публичный bucket `master-assets` (JPG/PNG/WebP, до 5 МБ); Storage INSERT ограничен папкой `masters.id` и `private.can_manage_master`. Публичная страница отображает фото, обложку, специализацию, теги и выбранную тему.
- Конструктор показывает реальный статус и URL `/pro/{slug}`; Master_pro может включать и отключать публикацию только собственной индивидуальной страницы.
- Owner управляет публикацией индивидуальных страниц Master_pro из административного раздела. Admin не видит индивидуальные страницы Master_pro и не может менять их `masters.is_active`; серверный триггер БД дополнительно запрещает такую операцию.
- `masters.photo_url` и `masters.cover_url` содержат публичные URL объектов `master-assets`.
- `/demo/**` использует демонстрационные данные и не является рабочим контуром бронирования.
- PostHog project создан, но frontend SDK и события аналитики пока не интегрированы.

## 9. CI/CD и миграции

- Ветка разработки/публикации: `main`.
- GitHub Pages workflow собирает frontend и публикует `dist`.
- Backend workflow разворачивает все восемь Edge Functions при изменении их исходников.
- CI использует Node.js 22 и Supabase CLI 3.0.0, запускает disposable local Supabase stack, применяет все миграции с нуля, выполняет pgTAP и Deno checks.
- Файлы `supabase/migrations` должны совпадать по timestamp/version с историей hosted Supabase.
- Уже применённые миграции не редактируются. Новые изменения добавляются новой миграцией.
- Не используйте Supabase CLI v3 для hosted-операций без явного `--project-ref` и подтверждения `--yes` в CI: CLI v3 изменил безопасные значения по умолчанию.

## 10. Известные ограничения перед production

1. Нужно включить Leaked Password Protection в Supabase Auth settings.
2. Требуются сквозные тесты реальных пользовательских сценариев Owner/Admin/Master_pro/Master.
3. Требуется проверить пользовательский сценарий публикации через Owner и Master_pro, а также фактическое бронирование после добавления реальных услуг и расписания.
4. Нужен интерфейс редактирования `booking_settings.rules_text`.
5. Требуется подключить PostHog SDK и реальные события.
6. После первых реальных нагрузок повторно оценить индексы и производительность; статистика пустых таблиц пока не показательна.
