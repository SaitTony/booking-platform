# Booking Space — архитектура проекта

Документ фиксирует согласованные продуктовые и технические решения перед реализацией базы данных и авторизации.

## 1. Технологическая архитектура

- Frontend: React + TypeScript + Vite + React Router.
- Публикация frontend: GitHub Pages.
- Backend: Supabase (PostgreSQL, Auth, Storage, Edge Functions).
- Защита данных: Supabase Row Level Security (RLS), ограничения и серверные функции.
- Секретный service-role key хранится только на серверной стороне в секретах Supabase. Его нельзя помещать во frontend, GitHub Pages или публичные переменные Vite.

GitHub Pages остаётся подходящим вариантом для статического frontend при использовании Supabase как backend.

## 2. Роли и область ответственности

### Owner
Владелец платформы. Полный доступ ко всем компаниям, мастерам, сотрудникам, клиентам и записям. Только Owner:
- создаёт учётные записи;
- назначает и меняет роли;
- создаёт компании;
- включает и отключает компании;
- связывает учётные записи с компаниями и страницами мастеров;
- сбрасывает пароли конкретных пользователей.

### Admin
Руководитель одной компании. Управляет страницей компании и страницами мастеров внутри своей компании, но не создаёт учётные записи и не назначает роли.

### Master_pro
Самостоятельный мастер вне компании. Управляет собственной индивидуальной страницей, услугами, расписанием и темой.

### Master
Наёмный мастер конкретной компании. Просматривает собственные записи и историю клиентов, но не редактирует страницу, услуги или расписание и не отменяет записи.

Master_pro и Master — разные типы работы, не взаимозаменяемые роли.

## 3. Матрица прав

| Возможность | Owner | Admin | Master_pro | Master |
|---|---:|---:|---:|---:|
| Создавать учётные записи сотрудников | Да | Нет | Нет | Нет |
| Назначать и менять роли | Да | Нет | Нет | Нет |
| Создавать / включать / отключать компании | Да | Нет | Нет | Нет |
| Редактировать страницу и описание компании | Да | Да | Нет | Нет |
| Создавать и отключать страницы мастеров компании | Да | Да | Нет | Нет |
| Редактировать имя, текст и фото мастера | Да | Да | Да, свою страницу | Нет |
| Создавать и редактировать услуги | Да | Да | Да, свои | Нет |
| Редактировать расписание | Да | Да | Да, своё | Нет |
| Просматривать записи | Все | В своей компании | Свои | Свои |
| Отменять записи | Все | В своей компании | Свои | Нет |
| Просматривать клиентскую базу и историю | Все | В своей компании | Свои | Свои |
| Менять цветовую тему | Компании | Своей компании | Своей страницы | Нет |

Тема компании единая и наследуется всеми страницами её мастеров. У Master_pro отдельная тема.

## 4. Учётные записи и авторизация

- Самостоятельной публичной регистрации нет.
- Создавать учётные записи может только Owner из раздела «Пользователи» административной панели.
- Обязательные данные: имя, номер телефона и временный пароль.
- Вход: номер телефона + пароль.
- Номер телефона нормализуется в международный формат E.164 и уникален для учётной записи.
- При первом входе сотрудник обязан сменить временный пароль.
- Owner может сбросить пароль выбранного пользователя. После сброса пользователь получает временный пароль и обязан сменить его при следующем входе.
- Пользователь без назначенной роли / привязки не получает доступ к рабочим разделам панели.
- Создание пользователей и сброс паролей выполняются только защищёнными Edge Functions с service-role key на серверной стороне. Функции самостоятельно проверяют, что вызывающий пользователь — Owner.
- Роли и принадлежность к компании нельзя принимать из доверия к данным frontend.

### Первоначальная настройка Owner

Первый Owner создаётся контролируемым bootstrap-процессом через доверенную административную сессию Supabase. Обычный публичный endpoint для назначения себе Owner не создаётся. После безопасного назначения первого Owner все последующие учётные записи и назначения ролей выполняются через панель Owner.

## 5. Компании, страницы и связи с аккаунтами

- Компания — отдельная сущность с уникальным глобальным slug.
- Страница корпоративного мастера — отдельная сущность, связанная с компанией.
- Индивидуальная страница Master_pro находится в пространстве /pro/<slug>.
- Корпоративная страница мастера находится в пространстве /<company-slug>/<master-slug>.
- Создание страницы мастера не создаёт учётную запись.
- Admin может создать до 5 активных страниц мастеров в своей компании, указав имя до сохранения. Пустое имя запрещено и на frontend, и на сервере/в БД.
- Slug формируется из введённого имени после нормализации. При конфликте система предлагает изменить slug, не подставляя его молча.
- Owner позднее создаёт аккаунт и связывает его с нужной компанией и/или страницей.
- У Master_pro индивидуальная страница; у Master — корпоративная страница. У одной страницы мастера может быть не более одной связанной учётной записи.
- Удаление мастера — архивирование, чтобы сохранялась история записей.
- Отключение компании скрывает её публичные страницы и блокирует новые записи; история сохраняется.

## 6. Клиентская база

- Единая клиентская база платформы.
- Один нормализованный телефон E.164 — одна карточка клиента.
- Клиент не создаёт аккаунт и не входит в систему; при бронировании указывает имя и телефон.
- Связи записей с клиентом сохраняются между разными мастерами.
- Master видит только клиентов и историю собственных записей.
- Admin видит клиентов и историю в пределах своей компании.
- Owner имеет полный доступ.
- Наличие общей карточки клиента не означает общего доступа к ней.

## 7. Бронирование и расписание

- Горизонт записи: 30 дней.
- Минимальное время до начала: 10 минут.
- Шаг расписания: 15 минут.
- Часовой пояс задаётся для мастера.
- Одна услуга на одну запись.
- Длительность услуги хранится в поле duration.
- Повторяющееся расписание и исключения дат (отпуск, выходной, особые часы).
- Запись автоматически подтверждается.
- Двойное бронирование и пересечения блокируются на сервере/в БД, а не только интерфейсом.
- Перед подтверждением клиент видит правила записи.
- Клиент не может самостоятельно отменить или перенести запись; обращается к мастеру.
- В записи сохраняются snapshot названия услуги, цены и длительности на момент бронирования.
- Создание записи проходит через защищённую серверную функцию / RPC с проверкой доступности, правил, услуги, телефона и временного интервала.

## 8. Предварительная модель данных

Ожидаемые основные сущности:
- profiles — учётные записи сотрудников и состояние первого входа / смены временного пароля.
- companies — компании и их настройки, включая общую тему.
- company_members — роли Admin и Master в конкретной компании.
- masters — публичные страницы индивидуальных и корпоративных мастеров.
- clients — единая клиентская база с уникальным нормализованным телефоном.
- services — услуги мастеров.
- working_hours — регулярное расписание.
- schedule_exceptions — исключения расписания.
- bookings — записи со snapshot-данными.
- При необходимости: история статусов записей, настройки бронирования, вспомогательные функции, триггеры и индексы.

Окончательные поля, внешние ключи, ограничения, индексы, триггеры, политики RLS и функции будут определены в SQL-миграциях после отдельной проверки схемы.

## 9. Порядок реализации

1. Спроектировать и проверить SQL-схему, связи, ограничения и RLS.
2. Создать первую миграцию и безопасно развернуть базовую структуру Supabase.
3. Реализовать Auth по телефону и паролю, bootstrap Owner, создание пользователей, смену и сброс временных паролей.
4. Реализовать роли и защищённую административную панель.
5. Подключить управление компаниями, страницами мастеров, услугами, расписанием и темами.
6. Подключить клиентскую базу и реальное бронирование.
7. Проверить сценарии всех ролей, безопасность, мобильную версию и публикацию.

Изменения в базе сначала проверяются в отдельной миграции и не выполняются вслепую в production.
